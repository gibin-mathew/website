Approach

Three rules I don't break

I picked these up by shipping systems that operations teams use every day.

Configuration beats code

When the hard part is variety (70+ web portals, catalogue data that won't sit still), I'd rather the system absorb new cases as data. Adding a new portal shouldn't need a deployment.

Seen in: portal automation

Put people where judgment lives

I send OTPs, CAPTCHAs, document checks and AI drafts to a person, on purpose. Automation earns trust when it knows when to stop.

Seen in: AI validators, portal automation

Measure what the system controls

If a user cancels a job, that's their call, so I don't count it as a platform failure. I'd rather improve an honest number than defend a flattering one.

Seen in: portal automation

Config-driven RPA across 70+ web portals

My role

Read the full case study →

Each submission meant someone retyping the same details into yet another web portal. About 30 minutes a time.

The problem

Our teams submit to dozens of external portals, and no two of them behave alike. Fields, page flows, upload rules and verification steps all change from site to site. If I'd written one bot per portal, the codebase would've grown with every new site and broken whenever one got redesigned.

The data didn't help either. Our CRM keeps a full name in one field, countries as codes and dates in one format, and every portal wants something different.

How one job runs
  1. 1
    PickAn operator picks the record and the portalOne click from a browser side panel.
  2. 2
    PrepareThe data is cleaned and mappedRaw CRM values are reshaped for this portal. Anything missing is flagged before the bot starts.
  3. 3
    FillThe bot fills the form, page by pageIt follows the portal's config, skips questions that don't apply and retries if a page is slow.
  4. 4
    Hand overA person steps in only when neededOTPs, CAPTCHAs and uploads. The bot waits, then picks up where it stopped.
  5. 5
    DoneSubmitted and loggedEvery step's outcome is recorded against the job and the team.

Calls I made

  1. New portals come in as configuration.A new portal is added as config, in a workflow editor we built. Coverage grew to 71 portals while the codebase stayed the same size, and config changes never needed a redeploy.
  2. Clean the data once, before the bot starts.A Python step turns raw CRM data (names, dates, country codes, phone numbers, yes/no answers) into portal-ready values. The bot never touches messy data, and missing fields show up before a run, not halfway through it.
  3. Let the page decide which questions apply.Portals show and hide questions based on earlier answers. Rules in the config (if this is on the page, if that step worked, repeat until the list runs out) check what's really there and skip the rest, so one config covers every branch of a form.
  4. I designed the human steps in from day one.OTPs and CAPTCHAs go to a person, and the bot picks up again once they're done. Trying to automate those steps would have made the whole thing fragile. Small failures, like a slow page, retry on their own with a growing wait.
  5. Every failure gets a label.When a run fails, the platform reads the error and tags it: a config problem, a portal that changed, a connection issue, or something that needs a person. The fix goes to the right person on the first try, not after a round of guessing.
  6. I defined success so it can't flatter us.Success rate is successful jobs divided by successful plus failed. If a user stops a job on purpose, it doesn't count against the platform.

Markdown Extractor: every website, one format an AI can read

No two websites lay out their data the same way. So instead of one scraper fighting all of them, an agent writes a scraper for each site, and every scraper hands back the same thing: clean Markdown.

The problem

Our data comes from a long list of catalogue websites. Some load content as you scroll. Some hide it behind cookie banners. Some tuck the useful parts inside page scripts. Hand-written scrapers were slow to build, they'd break without telling anyone, and each one returned data in its own shape.

What I built

We hand a new website to the Hermes agent, and it writes a Playwright scraper. Each one sits on a shared library for the boring parts (cookies, scrolling, retries, rate limits) and turns every page into a Markdown file, with a header saying where it came from and when. The files land in Amazon S3.

I split the platform into a few small services. One schedules the runs, one executes them, one streams the logs live to a React dashboard, and one pulls in new scraper code the moment it's pushed to Bitbucket. Nobody's deploying by hand.

Then the Markdown feeds a second agent. You ask it questions in plain language and it answers from the files. You don't write a query in SQL or anything else.

Subject Validator: AI reads the page, a person signs off

My role
Designed the review workflow and where the AI hands over to a person
Models
Gemini, Gemma and DeepSeek, picked per run
ReactTypeScriptNode.jsExpressMongoDBGeminiDeepSeek

Subject requirements are written differently on every page. Reading them all by hand didn't scale. Letting an AI publish them unchecked wasn't an option.

The approach

Our editors pick a model (Gemini, Gemma or DeepSeek, from lighter to heavier), tweak the prompt if a page needs it, and run it. The prompt is shared and versioned, so everyone can see who changed it last and when.

The AI gives back two things: a text summary and a structured table. Both are interactive, so you don't just read them, you edit them. The editor checks them against the highlighted source page, fixes any cell in the JSON editor, and saves. Then a subject identifier maps every subject it found to our master list. Exact matches publish on their own. Everything else shows its closest match, and a person picks.

Bulk reruns, per-person stats and token spend per run live in the same tool. Honestly, calling a model was the easy part. The real work was deciding what it's allowed to do alone.

Fees Validator: find the fee, check it once, apply it everywhere

Designed the review workflow and the bulk-apply rules
AI
Summariser that pulls out and highlights fees
ReactTypeScriptViteExpressMongoDBLLM summariser
Read the full case study →

Fee pages bury the numbers inside paragraphs. And one fee often applies to dozens of intakes, so typing it into each one by hand is exactly how mistakes creep in. I wanted it checked once.

The approach

We put the scraped fee page on the left. One shortcut (Shift + A) runs the AI summariser, which pulls the fees out and highlights every amount, date and condition, including the slippery words like "may". On the right is each intake with its fee field.

Our reviewer compares the two, then accepts the fee or fixes it. When it's right, one click applies it more widely: to every intake, to every full-time intake, or to every intake at the same campus. Then Verify. Each record keeps who verified it and when, so there's never a question about who signed off. A dashboard tracks progress by source and by person.

This research would have needed a floor full of people. One crawler did it.

The problem

To collect companies' official social-media handles, researchers had to visit websites one at a time. Across S&P's company universe that meant millions of visits.

What I built

I wrote a Python and Selenium crawler that ran across 3.4M+ company websites. Domain resolution made sure it hit the right site, and de-duplication left each company with one clean answer. It was the biggest of my S&P automations, which together came to about 168 FTE of capacity.
